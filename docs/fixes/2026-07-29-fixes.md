## Fix-001: 应用启动白屏

**日期：** 2026-07-29  
**严重程度：** 关键  
**发现方式：** 用户反馈

### 问题描述

`npm run dev` 启动后应用窗口显示白屏，内容为 "Claude Code Desktop" 纯文本标题，React 渲染进程未加载。

### 根因

`src/main/index.ts` 的 `createWindow()` 函数残留了任务 1（脚手架）的占位代码：

```typescript
mainWindow.loadURL('data:text/html,<h1>Claude Code Desktop</h1>')
```

没有根据开发/生产模式区分加载来源。任务 1 只是为了验证 Electron 窗口能启动，到了任务 12（App 根组件），主进程入口应该更新为加载 React 渲染进程，但子智能体遗漏了这个改动。

### 修复方案

将 `createWindow()` 改为标准的 electron-vite 模式：

- **开发模式：** `loadURL(process.env['ELECTRON_RENDERER_URL'])` → 连接 Vite dev server
- **生产模式：** `loadFile(join(__dirname, '../renderer/index.html'))` → 加载构建产物

同时补充了 `minWidth/minHeight`、`backgroundColor`、`shell.openExternal`、`ready-to-show` 等之前遗漏的配置。

### 涉及文件

- `src/main/index.ts` — 重写 `createWindow()` 函数

### 验证

- `npx tsc --noEmit -p tsconfig.node.json` ✅
- `npx tsc --noEmit -p tsconfig.web.json` ✅
- `npx electron-vite build` ✅ main(13.70 kB) + preload(2.29 kB) + renderer(835.73 kB)

## Fix-003: claude 命令不存在导致主进程崩溃

**日期：** 2026-07-29  
**严重程度：** 关键  
**发现方式：** 用户反馈

### 问题描述

发送消息后 Electron 主进程崩溃，弹出错误窗口：

```
Uncaught Exception: Error: Cannot create process, error code: 2
at new WindowsPtyAgent(...)
at startChat(...)
```

错误码 2 = 系统找不到 `claude` 命令。

### 根因

`claude-manager.ts` 的 `startChat()` 直接调用 `node-pty.spawn('claude', ...)`，没有 try/catch。当 Claude CLI 未安装时，`spawn` 抛出未捕获异常，导致整个 Electron 主进程崩溃。

### 修复方案

1. 新增 `isClaudeAvailable()` 函数：在 spawn 前先通过 `where claude`（Windows）或 `which claude`（Unix）检查命令是否存在
2. 用 try/catch 包裹 `spawn()` 调用
3. 两种情况都通过 IPC `chat:error` 通道报告给渲染进程，显示中文友好的错误提示，而不是崩溃

### 涉及文件

- `src/main/claude-manager.ts` — 新增 spawn 前的检查和 try/catch

### 验证

- `npx tsc --noEmit -p tsconfig.node.json` ✅
- `npx electron-vite build` ✅

## Fix-004: stream-json 解析格式与实际 CLI 输出不匹配

**日期：** 2026-07-29  
**严重程度：** 关键  
**发现方式：** 用户反馈（CLI 返回数据但界面无显示）

### 问题描述

`claude-manager.ts` 的 JSONL 解析器假设 Anthropic API 格式（`content_block_delta`/`text_delta`），但实际 Claude Code CLI 的 `stream-json` 输出是渐进式完整消息格式：

- `type: "system"` — 系统事件（初始化、thinking_tokens 等），应跳过
- `type: "assistant"` — **渐进式完整消息**（每次包含全部已有内容，非增量 delta）
- `type: "result"` — 最终结果

不匹配导致解析器从未进入 `content_block_delta` 分支，所有消息被 catch 块吞掉。

### 根因

1. **错误的事件模型**：代码按 API 的 delta 模型写，CLI 发的是 progressive full replacement。
2. **`return` 替代 `continue`**：系统事件用 `return` 退出了整个外层的 for 循环。
3. **未处理 ANSI 转义码**：pty 输出包含大量终端控制码，混入 JSON 导致 parse 失败。
4. **缺少调试日志**：解析失败在 catch 块静默丢弃，无法定位。

### 修复方案

1. 重写解析逻辑为差值算法：对比当前 `assistant.text` 和已累积内容，只发送增量
2. 将 `system` 事件的 `return` 改为 `continue`
3. 新增 `clean()` 函数过滤 ANSI 转义码
4. 在主进程（claude-manager）和渲染进程（AppContext）加 `console.log` 调试日志

### 涉及文件

- `src/main/claude-manager.ts` — 重写解析逻辑，加日志
- `src/renderer/src/context/AppContext.tsx` — 加日志

### 验证

- `npx tsc --noEmit -p tsconfig.node.json` ✅
- `npx tsc --noEmit -p tsconfig.web.json` ✅
- `npx electron-vite build` ✅

## Fix-005: Windows 上 cmd 命令 spawn 拆分

**日期：** 2026-07-29  
**严重程度：** 关键  
**发现方式：** 用户反馈（Windows 上 CLI spawn 失败）

### 问题描述

`node-pty.spawn('claude')` 在 Windows 返回 errno 2（找不到命令），即使 `where claude` 能找到。

### 根因

`claude` 是 npm 全局安装的 `.cmd` 批处理文件，`node-pty` 的 `spawn` 不会自动解析 `.cmd` 扩展名（不像 `child_process.spawn` 那样走 shell）。

### 修复方案

1. Windows 上通过 `cmd.exe /c claude ...` 方式 spawn
2. 新增 `findClaudePath()` 函数检查命令是否存在

### 涉及文件

- `src/main/claude-manager.ts` — spawn 方式改造

### 验证

## Fix-008: React 闭包导致 IPC 回调读到过期 state —— onChatDone 无法持久化 assistant 消息

**日期：** 2026-07-29  
**严重程度：** 关键  
**发现方式：** 用户反馈（对话历史只有 user 消息，assistant 回复丢失）

### 问题描述

`messages.jsonl` 中只有 user 消息、没有 assistant 回复。每次关闭重开，历史对话只能看到用户输入，Claude 的回复全部丢失。

### 根因#1: React 闭包 stale state

`onChatToken`/`onChatDone` 在 `useEffect([loadSessions])` 中注册一次，闭包捕获了注册时刻的 `state`。之后 state 更新（消息增多、streamingAssistantId 变化），但回调读取的永远是初始空值。

**根本原因**：React 的 `useState`/`useReducer` 返回的值是快照，闭包不会自动跟随最新值。

**修复**：使用 `useRef` 存 state 的实时引用（`stateRef.current = state`），所有 IPC 回调从 `stateRef.current` 读取。

### 根因#2: FINISH_STREAMING 先于 onChatDone 执行

`onChatDone` 调了 `dispatch({type:'FINISH_STREAMING'})` 把 `streamingAssistantId` 设为 null——然后回调继续用这个 null 去 `messages.find(m=>m.id===null)` 当然找不到。

**修复**：`FINISH_STREAMING` 不再清 `streamingAssistantId`，保留它供 onChatDone 查找；另外改用 `data.messageId`（主进程传回的 assistant 消息 ID）而不是 `state.streamingAssistantId`。

### 根因#3: messageId 不匹配

渲染进程生成的 `assistantId` 和主进程在 `spawnChat` 里独立生成的 `messageId` 是两个不同值，`data.messageId` 永远对不上 messages 数组里的 placeholder id。

**修复**：`SendMessageParams` 新增 `assistantMessageId` 字段，渲染进程预先生成 assistant ID 传给主进程，主进程用这个 ID 发送 `ChatTokenEvent` / `ChatDoneEvent`。

### 涉及文件

- `src/shared/types.ts` — SendMessageParams 新增 assistantMessageId
- `src/main/claude-manager.ts` — messageId = params.assistantMessageId || fallback
- `src/renderer/src/context/AppContext.tsx` — useRef 取代闭包 state；sendMessage 传 assistantMessageId；FINISH_STREAMING 保留 streamingAssistantId

### 经验教训

**Electron IPC 回调在 React 中使用时，永远不要直接读 state。用 `useRef` 存实时快照。** 这是一个非常常见的坑。IPC 回调不是 React 渲染周期的一部分——它们是外部事件，在注册时就决定了闭包，永远不会自动更新。

### 验证

- `npx tsc --noEmit` ✅
- `npx electron-vite build` ✅
- 用户确认 messages.jsonl 中 assistant 消息正常持久化

## Fix-009: ANSI 转义码导致 JSON 解析失败 —— 消息不显示

**日期：** 2026-07-29  
**严重程度：** 关键  
**发现方式：** 用户反馈（发送消息后界面无任何响应）

### 问题描述

发送消息后界面不显示任何回复。主进程日志显示 `sanitize` 后的 buffer 里只有 `system` 类型的事件，`assistant` 和 `result` 都解析不出来。raw pty 数据包含大量 ANSI 终端控制序列。

### 根因

1. **ANSI 转义码未完全清除**：pty 输出的 ANSI 序列包括 DEC private modes（`ESC[?9001h`、`ESC[?25l`）、CSI sequences（`ESC[2J`、`ESC[H`）、OSC title sequences（`ESC]0;claudeBEL`）。原来的 `sanitize` 函数处理顺序不正确——CSI regex 先跑了，DEC private mode regex `[hl]` 只能匹配以 `h` 或 `l` 结尾的序列，无法匹配 `ESC[2J`（J = clear）、`ESC[m`（m = reset）等。

2. **换行截断 JSON 对象**：pty 输出因为终端列宽有限（cols 160），长 JSON 行被强制打断。之前改用 bracket-depth 扫描 `{}` 边界解决了这个问题。

3. **`--no-ansi`、`-f json` 等标志不是 Claude Code CLI 的有效选项**。

### 修复方案

重写 `stripControlChars` 函数：
```typescript
function stripControlChars(data: string): string {
  return data
    .replace(/\x1b\[[\?>]?[0-9;]*[a-zA-Z]/g, '')  // 所有 CSI/DEC 合并处理
    .replace(/\x1b\][^\x07]*\x07/g, '')            // OSC BEL-terminated
    .replace(/\x1b\][^\x1b]*\x1b\/g, '')          // OSC ST-terminated
    .replace(/\r\n?/g, '\n')
    .replace(/[\x00-\x09\x0b\x0c\x0e-\x1f]/g, '')  // 低控制字符
    .replace(/\x1b/g, '')                           // 残留 ESC
}
```

关键改法：把 DEC private mode（含 `?`/`>` 前缀的 CSI 序列）和普通 CSI 合并到一条 regex `[\?>]?` 可选前缀中。原来分开写 + 顺序不对导致 DEC 序列没被匹配到。

### 涉及文件

- `src/main/claude-manager.ts` — 重写 stripControlChars 函数

### 验证

- `npx tsc --noEmit` ✅
- `npx electron-vite build` ✅
- 用户确认数据返回后界面正常显示
